# React+Spring 통합기 1부: 좌충우돌 초기 연동과 인증 기능 구현

## 서론: 야심 차게 시작한 통합 작업, 그리고 거대한 빙산

안녕하세요! 개인 프로젝트로 축구/풋살 매칭 플랫폼 "PlayMatch"를 개발하고 있습니다. 처음에는 빠른 개발을 위해 React(Vite)로 만든 프론트엔드와 Spring Boot 백엔드를 별개의 저장소에서 진행했습니다. 각자의 기능이 어느 정도 구현된 지금, 통합 개발 및 배포를 위해 두 프로젝트를 하나의 저장소로 합치는 작업을 시작했습니다.

간단할 줄 알았던 이 작업은 `404 Not Found`부터 `403 Forbidden`, 데이터베이스 `NOT NULL` 제약 조건 위반까지, 풀스택 개발의 모든 단계를 아우르는 거대한 트러블슈팅의 서막이었습니다.

이 글은 그 좌충우돌의 여정을 기록한 첫 번째 파트입니다. 분리된 두 프로젝트를 합치고, 가장 기본적이면서도 가장 중요한 **사용자 인증(회원가입, 로그인) 기능**을 완성하기까지의 과정을 생생하게 담았습니다.

## 1단계: 프로젝트 통합과 Git Subtree

가장 먼저 할 일은 두 개의 Git 저장소를 하나로 합치는 것이었습니다. 프론트엔드 프로젝트를 백엔드 프로젝트의 하위 디렉터리로 가져오기로 결정했고, `git subtree` 명령어를 사용했습니다.

```bash
# backend 프로젝트 루트에서 실행
git subtree add --prefix=frontend <프론트엔드 깃 주소> <브랜치명>
```

`git subtree`는 프로젝트의 히스토리를 그대로 유지하면서 하위 디렉터리에 병합할 수 있어 매우 유용합니다.

### 첫 번째 트러블슈팅: `working tree has modifications`

하지만 시작부터 에러가 반겨주었습니다. `git subtree`는 워킹 디렉터리가 깨끗한 상태에서만 실행할 수 있는데, 커밋하지 않은 변경사항이 있다는 것이었습니다.

`git status`로 확인해보니, 로컬 데이터베이스와 Redis의 데이터 파일들이 담긴 `pgdata`, `redisdata` 폴더가 Git에 의해 추적되고 있었습니다. 이 폴더들은 개발 환경에서 계속 변경되며, 저장소에 포함되어서는 안 되는 파일들입니다.

-   **문제:** Git이 추적하지 말아야 할 데이터 폴더를 추적하고 있음.
-   **해결:**
    1.  `.gitignore` 파일에 `pgdata/`와 `redisdata/`를 추가.
    2.  `git rm --cached -r pgdata redisdata` 명령어로 이미 추적 중인 파일들을 Git 인덱스에서만 제거. (로컬 파일은 삭제되지 않습니다.)

이 간단한 조치 후, 워킹 디렉터리는 깨끗해졌고 성공적으로 `subtree` 병합을 완료할 수 있었습니다.

## 2단계: 서버 연동과 보이지 않는 벽, 404 Not Found

이제 프론트엔드와 백엔드 서버를 동시에 띄우고 API 연동을 확인할 차례입니다.

-   프론트엔드 서버: `localhost:5173`
-   백엔드 서버: `localhost:8080`

회원가입을 시도하자마자 브라우저 콘솔에 `404 Not Found` 오류가 나타났습니다.

### 두 번째 트러블슈팅: 백엔드 주소를 모르는 프론트엔드

-   **문제:** 브라우저 개발자 도구의 네트워크 탭을 확인해보니, API 요청이 백엔드 주소인 `http://localhost:8080/api/auth/register`가 아닌, **프론트엔드 서버 자신**인 `http://localhost:5173/api/auth/register`로 전송되고 있었습니다. 프론트엔드 서버에는 API가 없으니 당연히 404 오류가 발생한 것입니다.
-   **해결:** Vite 프로젝트에서는 `.env` 파일에 환경 변수를 설정하여 이 문제를 해결합니다. 프론트엔드 프로젝트 루트(`frontend/.env`)에 백엔드 주소를 명시해주었습니다.

    ```
    VITE_API_BASE_URL=http://localhost:8080
    ```

    그리고 이 환경 변수를 사용하도록 `src/services/api.ts`의 `baseUrl` 설정을 확인했습니다.

    ```typescript
    // api.ts
    const baseUrl = import.meta.env.VITE_API_BASE_URL || "";
    ```

### 세 번째 트러블슈팅: 아키텍처의 배신, `axios` 직접 호출

`.env` 파일을 설정하고 프론트엔드 서버를 재시작했지만, 문제는 해결되지 않았습니다. 여전히 요청은 `localhost:5173`으로 향했습니다.

-   **문제:** 환경 변수가 제대로 적용되지 않는 원인을 찾기 위해, `SignupPage.tsx` 코드에 `console.log`를 추가하여 환경 변수가 제대로 읽히는지 확인했습니다. 놀랍게도, `VITE_API_BASE_URL` 값은 `http://localhost:8080`으로 잘 출력되었습니다.
-   **진짜 원인:** `SignupPage.tsx`와 `LoginPage.tsx`가 중앙 API 관리 모듈인 `api.ts`를 사용하지 않고, **`axios`를 직접 import하여 사용**하고 있었습니다. `axios.post('/api/auth/register', ...)`와 같은 상대 경로 호출은 `baseUrl` 설정의 영향을 받지 않고 현재 페이지의 주소를 기준으로 요청을 보내게 됩니다.
-   **해결:** 각 페이지에서 `axios`를 직접 호출하는 코드를 모두 제거하고, `api.ts`에 정의된 `AuthService.register(...)`, `AuthService.login(...)`을 사용하도록 코드를 리팩토링했습니다. 이는 프로젝트의 API 호출 방식을 일관성 있게 유지하는 중요한 아키텍처 수정이었습니다.

## 3단계: 백엔드의 역습, 403과 500 오류

`404`의 벽을 넘자, 이번에는 백엔드가 `403 Forbidden`과 `500 Internal Server Error`를 뱉어내기 시작했습니다. 하지만 이것은 오히려 좋은 신호였습니다. 드디어 요청이 백엔드에 도착했다는 뜻이니까요!

### 네 번째 트러블슈팅: `403 Forbidden`

-   **문제:** API 요청이 백엔드에 도착했지만, Spring Security가 "인증되지 않은 사용자의 요청"이라며 막아버렸습니다.
-   **원인:** `SecurityConfig.java`에 회원가입이나 로그인처럼 인증 없이도 누구나 접근할 수 있어야 하는 경로에 대한 예외 처리가 없었습니다.
-   **해결:** `authorizeHttpRequests` 설정에 `/api/auth/**` 경로는 `permitAll()`을 적용하여 모든 요청을 허용하는 규칙을 추가했습니다.

### 다섯 번째 트러블슈팅: `role` 컬럼 `null` 오류

-   **문제:** 보안의 벽을 넘자, 이번엔 회원가입 요청에 대해 `500 Internal Server Error`가 발생했습니다. 백엔드 로그를 확인하니 `ERROR: null value in column "role" of relation "users" violates not-null constraint` 라는 메시지를 찾을 수 있었습니다.
-   **원인:** 이것이 바로 "프론트 정보와 DB 클래스가 맞지 않았던" 문제의 핵심이었습니다. 프론트엔드는 `role`(권한) 정보를 보내주지 않는데, 백엔드 `UserService`는 이 정보를 프론트로부터 받으려고 시도했습니다. (`role(requestDto.getRole())`) 결국 `User` 엔티티의 `role` 필드가 `null`인 상태로 DB에 저장을 시도했고, DB의 `NOT NULL` 제약 조건에 따라 거부당한 것입니다.
-   **해결:** `UserService.java`에서 `requestDto`에 의존하는 대신, `role(UserRoleEnum.USER)` 코드로 변경하여 모든 신규 가입자에게 **서버가 직접** `USER`라는 기본 권한을 부여하도록 수정했습니다. 중요한 데이터의 설정 책임은 프론트엔드가 아닌 백엔드에 있어야 합니다.

## 4단계: 대장정의 마무리, 그리고 허무한 컴파일 오류

모든 로직을 수정하고 다시 백엔드를 실행했을 때, `cannot find symbol UserRoleEnum`이라는 컴파일 오류가 발생했습니다. 이유는 허무하게도, `UserService.java` 파일에 `UserRoleEnum` 클래스를 `import`하는 구문을 빠뜨렸기 때문이었습니다.

```java
import com.playmatch.playmatch.domain.UserRoleEnum; // 이 한 줄을 추가하여 해결!
```

이 마지막 수정을 거치고 나서야, 드디어 회원가입과 로그인이 모두 성공적으로 동작하는 것을 확인할 수 있었습니다.

## 1부를 마치며: 앞으로의 여정

-   하나의 저장소에서 관리되는 프론트엔드와 백엔드 프로젝트
-   환경 변수를 통해 유연하게 백엔드 주소를 설정하는 프론트엔드 아키텍처
-   중앙화된 API 서비스를 통한 일관성 있는 API 호출 방식
